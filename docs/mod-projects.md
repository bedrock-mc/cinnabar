# Build and run a paired server mod

Create one Rust project, build one installation package, then run it locally:

```sh
cargo run -p devtool -- mod new cosmic
cargo run -p devtool -- mod build --project cosmic
cargo run -p devtool -- mod run --project cosmic
```

Install Rust's `wasm32-unknown-unknown` target first. `mod build` compiles the server
and client separately and writes `cosmic/dist/cosmic.cmod`. Add `--release` after
`--project cosmic` for optimized guest components. The package contains:

- `server/`: the server WASM, generated Experience manifest and server/shared assets.
- `client/cosmic.cxb`: the signed client bundle, checked by the client's verifier.
- `resource.mcpack`: ordinary block/item art generated by the existing local-server pack builder.
- `registry.json` and `messages/`: generated shared definitions and optional Go bindings.
- `package.json`: the complete SHA-256 inventory.

The first build creates `.local/publisher.seed`; later builds reuse it. Keep the
seed private. Only the signed client bundle and ordinary resource packs go to
players. The installation archive belongs on the server.

Install a package into a saved local-server world in one command:

```sh
cargo run -p devtool -- mod install cosmic/dist/cosmic.cmod --server /path/to/world
```

Start the existing local server with `-dir /path/to/world -addr 127.0.0.1:19132`.
It discovers installed mods, starts their existing Experience helpers and offers
their client parts. Keep `experience-runtime` and `cinnabar-cxb` beside the server,
or set `-experience-runtime` and `CINNABAR_CXB_BIN`. Installation refuses to replace
an existing mod. Stop the server and remove the old package directory under
`world/mods/<id>` before an operator-managed update. Saved block identities still
have to remain compatible.

`mod run` builds the package and client tools, replaces this project's development
installation, starts an offline loopback server, seeds the isolated client's bundle
cache and joins it. It uses `.local/world` and `.local/client` under the project;
the repository's normal carriers must already be prepared with `make assets`.
Closing the client stops the server and its Experience helpers. The ordinary
client consent and developer execution policy still apply.

## Entry points and isolation

The generated project has `src/server.rs`, `src/client.rs` and `src/shared.rs`.
The root module enables exactly one side with Cargo features. `#[experience_sdk::entry::server]`
marks an `impl Experience for Server` and generates its registration and registry
handshake. Add ordinary Experience callbacks to that implementation.
`#[experience_sdk::entry::client]` exports the `ClientPart` implementation. Its generated
`registry()` declaration keeps initialization behind shared-definition confirmation.

Assets under `assets/server/` are available only to the server and are excluded
from the client bundle. Assets under `assets/client/` are excluded from the server
artifact. Other assets are shared. Server-only asset constants are unavailable in
the client build; a cross-side reference fails compilation. Keep private code in
the server module and do not explicitly include it from shared or client code.

## Declare blocks and items

Place typed declarations in `src/shared.rs` and original PNGs in `assets/`:

```rust
#![project(id = "cosmic", permissions(messaging))]
use experience_sdk::{id, message::{BlockId, ItemId}};

/// A registered cube with one shared texture.
#[block(name = "Moon rock", texture = assets::ASSET_MOON_PNG, hardness = 2.0)]
pub const MOON_ROCK: BlockId = id!("cosmic:moon_rock");

/// A registered item with a generated icon reference.
#[item(name = "Moon key", icon = assets::ASSET_MOON_PNG, max_stack = 1)]
pub const MOON_KEY: ItemId = id!("cosmic:moon_key");
```

Omit block hardness for an unbreakable cube. Item stacks default to 64. Shared PNG
constants are required for ordinary content; private server assets cannot become
pack art. Missing or renamed assets fail generation. The server entry point
registers these declarations automatically; no Experience TOML or pack JSON is
authored by hand. The pack builder runs the actual server guest and validates its
registration before publishing a package.

`EntityId` and `WorldId` reserve typed definition keys for entity/world registration.
They do not register content or create live instances. A world definition remains
distinct from a world instance and the protocol's network dimension ID.
`examples/experiences/terminal-client` is the paired reference project; it retains
its client-host test terminal and adds declared server content.
Its `examples/experiences/terminal-client/assets/terminal.png` is original sample
art covered by this repository's license.

## Shared definitions

Edit `src/shared.rs`. Its annotations are input to the SDK build script, which
generates the module included by `experience_sdk::include_shared!()`:

```rust
#![project(id = "cosmic", permissions(messaging, world_draw))]

use experience_sdk::{id, message::WorldId};

/// A world definition shared with server code.
pub const MOON: WorldId = id!("cosmic:moon");

/// Requests travel; server code decides whether it is allowed.
#[message(id = "cosmic.travel", schema = 1, to_server)]
#[derive(Clone, Debug, PartialEq)]
pub struct Travel {
    #[field(max_bytes = 96)]
    pub world: WorldId,
    pub request: u32,
}
```

Use `to_client` for server updates. The generator produces channel declarations,
Rust `Message` implementations and Go structs from the same ordered fields.
Supported fields are `bool`, `i8/i16/i32/i64`, `u8/u16/u32`, `String`, `EntityId`,
`WorldId`, `BlockId`, `ItemId`, and `Vec<T>` of these scalar types. Strings and IDs require
`max_bytes`; lists require `max_items`. Optional integer `min` and `max` bounds
must fit the Rust type. A list of strings also needs `max_bytes` for each item.
Text bounds count UTF-8 bytes. Unsupported types and conditional definitions fail generation.

Keep imports, typed ID constants and message structs in the shared source; put
application functions in other modules. IDs name definitions and do not create live
worlds, entities, items or server handles. Send with
`experience_sdk::client::send_message(&Travel { ... })`. Import
`experience_sdk::message::Message` to decode records with `Travel::decode(record)`.
Both codecs check field counts, types and bounds; the host still validates signed channels.

## Optional Go bindings

The local server runs the Rust server half without author-written Go. For existing
Go integrations, unpack the installation archive and import its generated package. Its module path is
`cinnabar.local/<project>/messages`; use a local `replace` directive or move the
generated package under your server module. Rebuild both together when definitions change.
Keep the generated helper-source `replace` directive in the main server module too;
Go does not inherit dependency modules' replacements.

Each message implements the Dragonfly helper's `cinnabarext.Message`: `Route()`
selects its bundle, channel and revision, and `Encode()` returns its native record.
Use `ext.Send` and `ext.Broadcast` directly with these messages. `messages.TravelType`
provides the generated route and decoder for `cinnabarext.OnMessage`. The generated
Go module pins the helper and a compatible upstream Dragonfly version. Import it as
`github.com/hashimthearab/rust-mcbe/tools/localserver/cinnabarext`.

Before listening, register the definition handshake with
`messages.RegisterRegistry(ext)` and handle its returned error. Register application
receivers with `cinnabarext.OnMessage(ext, messages.TravelType, callback)`. Player
identity comes from the authenticated connection; schedule world access through
Dragonfly transactions. The helper owns routing, epochs, sequences and fragmentation.

`EncodeRecord()` and `(*Travel).DecodeRecord([]byte)` expose the same canonical wire
v2 positional payload for other transports. They use the helper's codec. Use the
generated `messages.PackageID` when a transport needs the owning bundle ID.

The scaffold's `ClientPart::registry` returns `shared::REGISTRY`. Initialization
sends a generated registry request, which the existing client sends after Ready.
`RegisterRegistry` answers it with the server's generated fingerprint. Authored
initialization and callbacks wait for that exact fingerprint.
A mismatch refuses initialization with a diagnostic; missing confirmation leaves
it waiting. Duplicate matching confirmations do not initialize twice. Changes to
fields, revisions, directions and typed IDs affect the digest. This check does not
authenticate players or replace server-side validation.

## Assets and personal mods

Put files in `assets/`. Complete paths generate constants: `assets/sky/stars.bin`
becomes `shared::assets::ASSET_SKY_STARS_BIN`. Each typed `Asset` has an indexed
`path` and compile-checked `bytes`. Missing or renamed files remove the old constant,
so stale references fail compilation. Ambiguous constant names and symlinks fail generation.

To move a personal mod into a client part:

1. Move portable drawing and state code into the scaffold's modules.
2. Move setup into `ClientPart::init`, keeping the generated registry confirmation.
3. Replace asset literals with generated constants and local-only inputs with typed messages.
4. Use the canonical drawing interfaces available to client parts, retaining shared
   personal SDK drawing types and following their grants and callback lifecycle.
5. Replace `export_player_mod!` with the scaffold's `#[client]` entry point and rebuild.

A personal-mod component is not a client-part component. Personal packet interception,
native extensions and local settings do not become server privileges. This build
command adds no drawing interfaces or server world/entity execution APIs.

## Migrate an earlier generated project

Earlier `mod build` outputs were directories containing a client `.cxb` and Go
messages. Builds now emit one `.cmod`; existing standalone `.cxb` bundles remain
supported by the low-level bundle tools and client runtime.

Add `client` and `server` Cargo features forwarding to the matching SDK features,
turn off default SDK features, and gate each module as the current scaffold does.
Replace the explicit client export macro with `#[experience_sdk::entry::client]` on its
implementation. Add a server implementation marked `#[experience_sdk::entry::server]`;
that attribute owns `register`, `registration` and `registry`. Move shared content
IDs to annotated block/item declarations and use generated asset constants.
The canonical server WIT is unchanged, so existing Experience artifacts keep their
supported runtime APIs.
